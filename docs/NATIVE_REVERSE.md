# Native per-track REVERSE

The [RC-505mkII Parameter Guide v1.2](https://static.roland.com/assets/media/pdf/RC-505mk2_Parameter_eng03_W.pdf) defines REVERSE as conventional or reverse playback and states that an enabled reverse track cannot enter overdubbing after recording. Native follows that behavior: its playback cursor reads the existing phrase from the last PCM frame toward the first, without reversing or rewriting the stored PCM. REC->DUB falls back to REC->PLAY for a reverse track, and a playing reverse track rejects an overdub command.

REVERSE is per track, saved in Native Memory, and configured through the existing `/v1/native-loop-transport/config` request using an optional boolean `reverse` field. Old callers and Memory envelopes that omit it retain forward playback. `expectedRevision` is also optional to preserve the legacy full-config request contract; new field-specific UI updates include it and the host rejects stale revisions, while legacy callers that omit it retain the prior last-write-wins behavior and should send a complete config. The host publishes requested/applied/fault revisions and `loopTransportAppliedReverse`; the UI enables the control only when that callback readback exists. Changes require the track to be stopped. The audio callback applies the setting through the existing bounded command queue; reading reverse adds no allocation, lock, or PCM copy.

`1SHOT` counts playback progress, so reverse 1SHOT plays the phrase once from its last frame to its first and then stops. Repeating reverse playback wraps to the last frame. Native LOOP SYNC is limited to the Rhythm-phased REC/STOP slice documented in [NATIVE_LOOP_SYNC.md](NATIVE_LOOP_SYNC.md); this reverse feature does not enable synchronized playback or reverse recording under LOOP SYNC. Browser LOOP SYNC settings remain owned by the Browser runtime.

Software tests cover exact stereo frame order, one-shot completion, repeat wrap, overdub refusal, and preservation of the original PCM. These checks establish the Native code path only, not hardware parity or real-device callback timing.
