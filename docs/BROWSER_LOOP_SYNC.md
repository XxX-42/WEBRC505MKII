# Browser LOOP SYNC scope

Roland's [RC-505mkII Parameter Guide v1.3](https://static.roland.com/assets/media/pdf/RC-505mk2_Parameter_eng04_W.pdf), pages 3–4, defines LOOP SYNC per track. With LOOP SYNC ON, recording/playback follows the memory tempo or a synchronized track; the mode can start immediately, at a measure, or at a configured loop length. REC QUANTIZE applies only to recording: MEASURE aligns the recording start to a measure, while OFF starts immediately. In both modes, stopping a LOOP SYNC recording aligns its length to a measure. This grid is available when Rhythm is on, another recorded track has LOOP SYNC on, or MIDI Sync is on.

## Browser capture behavior

Browser recording quantization uses an audio-frame phase when one is verifiable. `Transport.getNextMeasureStartFrame()` calculates boundaries from the established master origin frame and an integer measure length in samples. For a synchronized slave track, REC with QUANTIZE MEASURE reserves the next boundary; stopping that take reserves a later boundary and asks the shared input-capture worklet to stop on that frame. The capture path checks readiness and phase/settings revisions, and accepts the scheduled start only after an exact worklet frame acknowledgement. If the required phase or capture path is unavailable, a quantized start is refused; a stop without a verifiable phase ends at the current capture frame and does not claim quantization. QUANTIZE OFF makes the start immediate, but a synchronized take may still quantize its stop, consistent with the guide.

The main-thread `Transport.start()` timer is separate: its 25 ms `setInterval` emits UI-oriented beat/measure events from `performance.now()`. It is not used as the audio-frame phase or as the Browser capture start/stop scheduler. These timer events are not sample-accurate phase evidence.

## Limits and evidence

The Browser currently establishes a master phase only for ordinary forward playback of a LOOP SYNC master whose loop is approximately one inferred measure long (within one frame), starts at offset zero, and has no Loop Transport FX or live pitch processing. The project does not retain enough measure-count metadata to establish a reliable phase for a multi-measure master loop. Because a one-frame length difference is accepted while the grid uses the inferred measure-frame count, repeated loop boundaries can diverge by a frame per pass in that edge case.

When Browser Rhythm is running, its real AudioWorklet publishes a phase snapshot only after a successful render block has covered the configured absolute measure origin. The snapshot includes that origin, the next measure frame, sample rate, BPM, steps per bar, and a worklet-owned epoch. The shared input-capture AudioWorklet uses this phase to reserve the same absolute frames for recording start and stop, and accepts a start only after an exact frame acknowledgement. REC QUANTIZE MEASURE reserves the next measure for start; OFF starts immediately. With LOOP SYNC ON, both settings align recording stop to the next measure, as described in the Parameter Guide. The snapshot object is prepared once when the Rhythm configuration changes and posted once when the origin is rendered; this is a one-time control message per configuration, not per-block telemetry. Exceptional timeline rewind/recovery diagnostics also post messages when those events occur.

Rhythm stop, reconfiguration, tempo change, and sample-timeline rewind/recovery invalidate the phase immediately. A queued quantized start is cancelled and the incumbent PCM is kept. If the phase changes while a future stop is queued, Browser replaces that stop with an immediate stop at the current capture frame; a stale result detected before commit is discarded, leaving incumbent PCM intact. These guards cover only Browser's controlled AudioWorklet timeline.

The Browser MIDI Clock control is currently a read-only monitor: incoming F8 pulses can be inspected, but they do not drive Transport tempo, phase, or record quantization. Thus the guide's Rhythm and MIDI Sync grid sources are not fully implemented in Browser. Classic LCD exposes the per-track LOOP SYNC switch; Native remains disabled until its backend supports it.

Native schedule requests are fenced by both the host-incarnation ID and the caller's observed per-track request revision; the host compares both while holding the scheduler command lock. On reconnect, a tab with its own receipt reconciles that exact revision, including terminal ACKs. Without a local owner receipt, a tab only reads host status and blocks on an unresolved request; it never cancels another tab's schedule. Incomplete status or multiple pending revisions also block Native startup. This receipt/recovery path does not enable Native LOOP SYNC or REC QUANTIZE: those controls remain disabled until their per-track Memory state and all documented start/stop modes are implemented.


[`browser-loop-sync-quantized-capture.spec.ts`](../tests/e2e/browser-loop-sync-quantized-capture.spec.ts) exercises both a generated master loop and the real Browser Rhythm and input-capture AudioWorklets in Chromium. It checks exact requested/acknowledged start frames, quantized stop length, and cancellation/stale-phase behavior that preserves incumbent PCM. This is software-path evidence only; it does not establish physical RC-505 timing or full hardware parity.
